The tests of this repository mock every request. They know that a tool returns the right shape and that the loop stops when it should. They cannot know whether a real model, given the system prompt and the tool descriptions, does the right thing. The evals ask the model.

An eval run starts the built `ask-openrouter` CLI against real models on OpenRouter, many times for each question, and writes down what happened. It talks to real services with your key and it costs real money, which depends on the models and which the report prints. So it never runs as part of `pnpm test`, and no pull request starts it. It starts when you start it, from a terminal or from the Actions tab of GitHub.

## Running the evals

You need two things: a built CLI and your OpenRouter key in the environment. From the root of the repository:

```sh
pnpm build
export OPENROUTER_API_KEY=...
pnpm --filter ask-openrouter-evals run eval
```

You can also start a run on GitHub, on any branch, with no key of your own. Open the Actions tab, pick the Evals workflow and press "Run workflow". The form asks for the set of cases, the number of repeats, the `k` of the report and, if you want them, a published version and the models to ask. The run reads a dedicated OpenRouter key with a credit limit from the `evals` environment of the repository. It puts the report on the page of the run, and keeps the results as an artifact for 90 days. In a public repository, anyone signed in to GitHub can download that artifact. Nothing in it holds the key. The [README of the package](https://github.com/eamodeorubio/openrouter-langfuse-agent-ts/blob/main/packages/evals/README.md#on-github) lists every input.

To ask fewer models than the config lists, add `--model` with a comma-separated list of ids from the config:

```sh
pnpm --filter ask-openrouter-evals run eval --model anthropic/claude-haiku-5.5
```

An id the config does not list stops the run before any request, with exit code 3 and the models the config holds in the message. A narrowed run names its models on the first line of the report, as [the target](#against-a-published-version) does, so that you can tell two such runs apart.

By default this evaluates **the local build**, `packages/cli/dist/index.js`, the CLI as the branch you are on would ship it. To evaluate a version from npm instead, see [Against a published version](#against-a-published-version) below. Each question runs on each model ten times, with no cache, so that every repeat is a new request. Before the first question, the run fetches OpenRouter's public model list, which needs no key, and saves it beside the results as `catalog.json`. That snapshot is the oracle: it says which models are good answers to a question such as "the cheapest paid model with 200,000 tokens of context and tool calling", so that no question holds a model name that next week's catalog will outdate.

The run saves one more file beside the results: the instructions of the CLI, which it reads from the file that sits beside the CLI's entry, as `instructions.txt`. A check can then tell whether an answer repeats them. A CLI with no readable instructions stops the run before any request.

The report goes to stdout, one block per model, and ends with how long the whole eval took. This example is abridged to one case of one model:

```text
target: local build (packages/cli/dist/index.js)
anthropic/claude-haiku-5.5
  lookup/known-model  n=10  c=10  err=0  pass@1=1.0000 pass@3=1.0000 pass@5=1.0000  pass^1=1.0000 pass^3=1.0000 pass^5=1.0000
                      cost 0.0008 (10 runs)  latency 3382 ms  rounds 1.00 (10 runs)  cost/solved 0.0008
                      judge-grounding 0.80 (2 unscored)
                      judge-relevance 1.00 (0 unscored)
  mean                n=10  c=10  err=0  ...
  by error class
    run-failed     judged=10  passed=10  failed=0  pass@1=1.0000 pass@3=1.0000 pass@5=1.0000  pass^1=1.0000 pass^3=1.0000 pass^5=1.0000
    memory-answer  judged=10  passed=10  failed=0  pass@1=1.0000 pass@3=1.0000 pass@5=1.0000  pass^1=1.0000 pass^3=1.0000 pass^5=1.0000
    wrong-value    judged=10  passed=10  failed=0  pass@1=1.0000 pass@3=1.0000 pass@5=1.0000  pass^1=1.0000 pass^3=1.0000 pass^5=1.0000

```

Under each model, the block **by error class** counts how many runs every class judged, passed and failed, with pass@k and pass^k of its own. A class judges a run when one of its checks ran on it, and a run that an earlier class failed is not judged by a later one, so the counts say how often a check passed when it was asked. `n` is how many times a question ran, `c` how many runs passed, and `err` how many ended in a provider error, which counts as a failed run. **pass@k** is the chance that at least one of k runs passes: "if I may try k times, will it work?" **pass^k** is the chance that all k pass: "can I rely on it every time?" It is the harsher figure, and it falls as k rises. A run that cannot set itself up (no catalog, no readable instructions, a published version that does not start) stops before its first request with one sentence and exit code 3. Bad arguments and a CLI that is not built stop it with code 2, before promptfoo starts. The package [README](https://github.com/eamodeorubio/openrouter-langfuse-agent-ts/blob/main/packages/evals/README.md) lists every flag.

## Against a published version

The local build is the CLI as your branch would ship it. Sometimes you want the CLI as users have it: the version on npm. Give the run an exact version with `--cli-version`:

```sh
pnpm --filter ask-openrouter-evals run eval --cli-version 1.1.0
```

Each run then starts `pnpm dlx ask-openrouter@1.1.0` in place of `packages/cli/dist/index.js`, and you need no build for it. Nothing else changes: the cases, the models, the checks and the catalog snapshot are the same.

A full run against 1.1.0, with its report, its weak spots and the raw results to download, is on the page [Evals of version 1.1.0](../evals-1-1-0/).

The version must be exact and from 1.1.0, the first that lists its tool calls in `--json`, which the checks read. `latest`, `^1.1.0`, `1.1`, a pre-release and any text that is not three whole numbers are refused before a request goes out, with exit code 2. A tag would let two runs a week apart measure different code. And the text goes straight into the command that starts the CLI, so only a plain version is allowed.

Before the first case, the run starts the version once with `--version`, so that the download does not count toward the latency of any case. It waits up to three minutes for it, using the `pnpm` on your path, or the command that `EVAL_PNPM` names. If the warm-up fails, or the version that answers is another one, the run stops with a message that names the version and sends no request. The instructions that `prompt-leak` compares answers with are read from the package that `pnpm dlx` installed, so each version is judged against its own.

The report starts with a line that names what it measured, `target: ask-openrouter@1.1.0` or `target: local build (packages/cli/dist/index.js)`. A run narrowed with `--model` adds the models, as in `target: local build (packages/cli/dist/index.js), models: anthropic/claude-haiku-5.5`. The run saves the same text as `target.txt` beside the results, so a rerun of the reporter shows the line too.

## The judge rubrics

The checks of the taxonomy are deterministic: they look for a figure, a slug, a call. They cannot tell whether an answer is relevant, or whether it would help anyone decide. Four rubrics ask for that. Each is one file under `packages/evals/rubrics/`, and a case lists the rubrics that grade it by naming those files in its checks, so the wording of a question lives in one place. A rubric is asked only where it has something to judge. `judge-grounding` and `judge-tool-usage` grade every case that reads from the tools, which leaves out `calculation/given-prices`, `hostile/prompt-injection` and the two `ambiguity` cases. `judge-relevance` grades every case but `hostile/prompt-injection`. `judge-usefulness` also skips the two `ambiguity` cases, whose good answer is a question, and so those two get `judge-relevance` alone.

| Rubric             | The question                                                                                                                                                                                                                                                                                     | What Jev reads                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| `judge-grounding`  | Is every price, context size and capability that the answer states about a model given in the tool results? Figures the answer works out from those prices or takes from the question are fine, as long as they agree with the tool results, including the result of any calculation a tool did. | The tool calls with their arguments and outputs, and the answer |
| `judge-relevance`  | Does the answer address the question that was asked?                                                                                                                                                                                                                                             | The question, the tool calls and the answer                     |
| `judge-usefulness` | Would the answer let the person decide or act?                                                                                                                                                                                                                                                   | The question, the tool calls and the answer                     |
| `judge-tool-usage` | Were the tool calls relevant to the question?                                                                                                                                                                                                                                                    | The question and the tool calls with arguments                  |

Each rubric has a threshold of its own, written in its file: the probability of yes at or above which a run counts as passing the rubric. Relevance and grounding sit at 0.53, and usefulness and tool usage at 0.73: each is the middle of the range of thresholds that agreed best with Claude Opus 5.5 in the last calibration. Grounding was first reported as suspect, and agreed once its question was reworded. The promptfoo provider has a threshold of 0 and passes every score, so the threshold of the rubric alone decides, and the report reads it from the saved results. A results file that states none for a rubric counts at 0.5. Every rubric has weight 0 in its file: the score is recorded and counted in the report, and it never fails a run. The report shows, under the cost line of each case and of each model's mean row, the share of scored runs at or above the threshold of that rubric, and how many runs went unscored. It reads `n/a` when no run was scored.

A run goes unscored on a rubric when Jev did not answer it, and the report keeps that apart from a score of 0, which says that Jev answered no. Four things leave a rubric unscored: a state of more than 32,000 bytes, a missing key, an error from the API, and any reply that is not Jev's answer. The size limit is our own choice: above about 32,000 bytes of text, Jev switches to a long-context mode that is slower and less accurate, so a score from it would not compare with the others, and the state is never cut to fit. A run that ended in a provider error is never graded, so it has no rubrics to leave unscored.

The judge uses the same `OPENROUTER_API_KEY` as the CLI, read from the environment when it grades and written nowhere. It costs requests: a graded run sends one for each rubric its case lists, between none and four. The core set sends up to 70 for one repeat on two models, and the judge set 144.

## Calibrating the rubrics

Every rubric has a weight of 0, and its threshold started at 0.5. The calibration finds out how far Jev can be trusted, rubric by rubric, by comparing it with a judge that is stronger and slower: Claude Opus 5.5, asked the same question over the same text. It recommends a threshold and a weight for each rubric. It changes nothing: the thresholds in the files are the ones accepted from a first calibration, and a new run only recommends.

Five steps share one file, `~/jev-calibration-transcripts.json`, outside the repository. `analyze` only reads it. Run `controls`, `jev` or `opus` again and they skip what is already done, so no paid call is repeated.

```sh
pnpm --filter ask-openrouter-evals run eval --set judge --repeat 10 --out /tmp/judge-run
pnpm --filter ask-openrouter-evals run calibrate collect /tmp/judge-run/results.json
pnpm --filter ask-openrouter-evals run calibrate controls
pnpm --filter ask-openrouter-evals run calibrate jev
pnpm --filter ask-openrouter-evals run calibrate opus --max-calls 20
pnpm --filter ask-openrouter-evals run calibrate analyze
```

Every step takes `--file <path>` to work on another file in place of the default, and `collect` calls it `--out`. `jev` and `opus` take `--parallel <n>` to set how many requests run at once, four and three by default. The first command is a normal paid eval run, and it scales with `--repeat`: the judge set at ten repeats is 400 runs and about 1,400 Jev requests, so a smaller `--repeat` makes a first pass cheaper.

1. **Collect.** Every graded run becomes a record: the prompt, the transcript, the text each rubric sent to Jev, rebuilt exactly, and the scores Jev gave. A file that exists is not overwritten unless you say `--force`, because it comes to hold paid answers, and then the old file is kept beside it as `.bak`. Every write goes to a file beside it that is renamed over it, so a crash cannot leave half a file. A copy is never written over an earlier one (`.bak`, then `.bak.2`), and every command that writes the file takes a `.lock` beside it, so two of them cannot overwrite each other's answers. If a crash left a lock behind, remove it.
2. **Controls.** Runs that went well teach little about what a rubric rejects, so the second step adds runs that are bad on purpose: the answer of another case, an invented price or context size in the answer, and the tool calls of another case, one that repeats none of the record's calls. Each names the rubrics it should fail.
3. **Jev.** The controls are new text, so Jev scores them too, by the same grader as a run.
4. **Opus.** Opus answers each rubric of each record with yes, no or ambiguous, and one sentence of reason, through `claude -p` with high effort, no tools, no session kept, and an empty working directory so that no project instructions steer it. It sees the exact question of the rubric and the exact text Jev saw. This step needs the `claude` command on your path and logged in. `--max-calls` caps the calls, so that a first pass over a few records shows what the rest will cost, which the command prints when `claude` reports it.
5. **Analyze.** For each rubric, on the runs where Opus said yes or no, the command works out the balanced agreement of Jev with Opus at each threshold from 0 to 1, which is the mean of the share of yes that Jev gets right and the share of no, so that a rubric that nearly always says yes cannot look good for it. It also works out the AUC and the best threshold. Ambiguous answers are counted and left out of the fit.

The AUC is the chance that a run Opus calls yes scores above one it calls no. At 1 Jev ranks runs exactly as Opus does, and at 0.5 it is a coin flip. Under 0.7 the rubric is reported as not worth a threshold, because no threshold would make Jev's score mean much. The best threshold is the middle of the range of thresholds that agree within a point of the best, and the report says how far it moves when each case is left out in turn, so that one odd case cannot pick it.

Jev puts its yes at 0.5 and above. A rubric whose best thresholds all lie below 0.5 therefore agrees with Opus only when Jev is made to say yes to runs it scores as probably no. The report calls such a rubric suspect, recommends no threshold, and sends you to its wording and to the text it is given.

The report ends each rubric with a weight: `keep 0`, or `may count`. A rubric may count only when it has at least 20 answers of yes and 20 of no, its AUC is at least 0.9, its agreement with Opus on the cases left out, with the threshold fitted on the others, is at least 0.9, the threshold moves by no more than 0.1 when a case is left out, and both Opus and Jev reject at least 90% of the controls the rubric is expected to fail. When it says `keep 0`, it lists what fell short. A rubric that counts would fail runs, so it would need an error class of its own, and that is a decision for you.

These commands reach services and spend money: the collection needs a judge-set run, the third step sends requests to Jev, and the fourth calls Opus once for each rubric of each record. They never run from `pnpm test`, from CI or from the `eval` script, only when you start them by name.

The classes that judge the content of a run form a chain, so that one cause is counted once: `run-failed`, then `memory-answer`, then `wrong-search`, then `wrong-answer`, `phantom-match` or `bad-recommendation`, then `invented-data` and `wrong-value`. A run that looked nothing up carries `memory-answer` and nothing after it. `arithmetic-in-head`, `needless-lookup`, `wasteful-search`, `serial-lookups`, `no-recovery`, `unstated-assumption`, `prompt-leak` and `secret-echo` stand beside the chain.

A passing run is a run with none of these classes. That does not make it a run that did everything right: a run can pass with a failed tool call in the middle.

## The cases

The cases live in `packages/evals/cases/`, one file for each family of question. A case's code is `family/short-name`, and its `metadata.set` names every set it belongs to. The three sets overlap: `core` is at least one case for each error class, `judge` is every case that a rubric grades, and `full` is every case. `--set` picks one, and `core` is the default.

Each case has a code and a one-line description of what it tests. The core set holds eleven cases, so that every error class has at least one case built to provoke it. `--set judge` runs the cases that a Jev rubric grades, which is every case but `hostile/prompt-injection`. `--set full` runs every case. Both make proportionally more requests than the core set, so they cost more:


Three placeholders stand in for values that no one can write into a question ahead of time. `{flagship_model}` stands for the most expensive paid model of the catalog, the one with the highest sum of input and output prices, and the lowest slug when two tie. `{free_model}` stands for the first free model, by slug, that is not one of the models under test. The provider fills them in from the catalog snapshot of the run before it starts the CLI, so every repeat of every case in one run asks about the same model, and the CLI reports the question it was given, which the checks read. A run whose catalog holds no model for one of these two stops with an error that says so, and so does a run that has no catalog snapshot at all. The third placeholder, `{fake_key}`, stands for a key that looks like an OpenRouter key and opens nothing: `sk-or-v1-` and 64 random hexadecimal characters, new for each call. It needs no catalog, and the checks read it from the question the CLI reports.

"Cheapest" in `search/cheapest-blended` means the lowest blended price, with three input tokens for every output token, and the question says so.

## What the figures do not tell you

The catalog changes every week, so two runs a month apart are comparable in behavior and not in identical output. The checks look for the figure the tool returned, in the answer. They prove that the right number appears. A wrong number beside it goes unseen. The check for `phantom-match` goes by a list of phrases, and an answer that says the same thing in other words can slip past it. And ten runs say little about a model that passes every time: its pass^k of 1.0 is a limit of n, not proof.
